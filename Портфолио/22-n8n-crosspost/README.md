# 22 — Кросс-постинг в каналы (n8n)

> **Статус: демо-заготовка для портфолио.**
> Рабочая ветка — публикация в **Telegram-канал**. Остальные платформы (VK и т.п.) —
> заготовки HTTP-нод с плейсхолдерами: их нужно допилить под конкретные API и токены.
> Проект рассчитан на **ваш** n8n на VPS (Docker + Postgres). Свой n8n поднимать не нужно.

## Идея

Владелец пишет пост **один раз** — через Telegram-бота-приёмник или веб-форму (вебхук).
n8n нормализует пост, кладёт его в очередь в Postgres и публикует в подключённые каналы.
Если задано время публикации в будущем — пост уходит в отложенные, и его в нужный момент
подхватывает отдельный воркфлоу-планировщик.

```
                 ┌─────────────────────────┐
  Веб-форма ─────▶  Webhook приёма поста     │
                 │                           │
  Telegram-бот ──▶  Telegram бот-приёмник    │
                 └───────────┬───────────────┘
                             ▼
                   Нормализация (Code)
                             ▼
                 Postgres INSERT → posts (queued)
                             ▼
                   IF: время публикации <= сейчас?
                     │ да                    │ нет
                     ▼                       ▼
        ┌────────────────────────┐   остаётся в очереди
        │ Telegram-канал (send)  │   (ждёт планировщика)
        │ + VK (заготовка, off)  │
        └───────────┬────────────┘
                    ▼
        Postgres UPDATE → published


  ┌──── scheduler.json (раз в минуту) ─────────────────────────────┐
  │ Schedule → SELECT queued AND publish_at<=now()                 │
  │        → Telegram-канал (send)                                 │
  │             ├─ успех → UPDATE published                        │
  │             └─ ошибка → UPDATE retry_count+1 / error           │
  └────────────────────────────────────────────────────────────────┘
```

## Структура проекта

```
22-n8n-crosspost/
├── workflows/
│   ├── crosspost.json    # приём поста → очередь → публикация сейчас
│   └── scheduler.json    # отложенная публикация по времени
├── db/
│   └── 001_posts.sql     # таблица posts + индексы + журнал post_logs
└── README.md
```

## Шаг 1. База данных

Примените миграцию к вашему Postgres:

```bash
# напрямую
psql -U <user> -d <db> -f db/001_posts.sql

# или в Docker
docker exec -i <postgres_container> psql -U <user> -d <db> < db/001_posts.sql
```

Создаются таблицы `posts` (очередь) и `post_logs` (журнал попыток) с индексами под выборку
«пора публиковать».

## Шаг 2. Credentials в n8n

Создайте в n8n (Settings → Credentials):

1. **Telegram API** (`telegramApi`) — токен бота от @BotFather.
   Этот же бот используется и как приёмник постов, и как публикатор в канал.
2. **Postgres** (`postgres`) — доступ к той же базе, куда применили `001_posts.sql`.

Задайте переменную окружения контейнера n8n с ID канала публикации:

```
TELEGRAM_CHANNEL_ID=@your_channel   # или числовой -100xxxxxxxxxxx
```

## Шаг 3. Импорт воркфлоу

В n8n: **Workflows → Import from File** — импортируйте оба файла:

- `workflows/crosspost.json`
- `workflows/scheduler.json`

После импорта в каждой ноде Postgres/Telegram выберите ваши credentials
(в JSON стоят плейсхолдеры `REPLACE_TELEGRAM_CRED_ID` / `REPLACE_POSTGRES_CRED_ID` —
n8n сам предложит подставить реальные при первом открытии).

Активируйте оба воркфлоу (переключатель **Active**). Скопируйте URL вебхука из ноды
«Webhook приёма поста» для веб-формы.

## Шаг 4. Как добавить канал

**Telegram (рабочий):**
1. Добавьте бота-публикатора **администратором** нужного канала (право «Публикация сообщений»).
2. Пропишите ID/username канала в `TELEGRAM_CHANNEL_ID`.
3. Готово — посты уходят в этот канал.

**Другие платформы (заготовки):**
В `crosspost.json` есть нода «Заготовка: VK wall.post» (HTTP Request, **disabled**).
Чтобы включить платформу: подставьте токен/ID сообщества в плейсхолдеры
(`PLACEHOLDER_VK_OWNER_ID`, `PLACEHOLDER_VK_ACCESS_TOKEN`), снимите «disabled»,
при необходимости продублируйте ноду под OK / Дзен / X и т.д. Список целевых
платформ поста хранится в поле `channels` (JSONB-массив).

## Формат входящего поста (веб-форма / вебхук)

`POST` на URL вебхука, JSON:

```json
{
  "text": "Текст поста (можно HTML)",
  "media_url": "https://...jpg",
  "media_type": "photo",
  "channels": ["telegram", "vk"],
  "publish_at": "2026-08-02T18:30:00Z"
}
```

- `publish_at` не задан или в прошлом → публикуется **сразу**.
- `publish_at` в будущем → пост ждёт в очереди, публикуется планировщиком.

Через Telegram-бота-приёмника достаточно просто написать боту текст/фото —
нормализация вытащит `text`/`caption`/`photo` сама.

## Статусы поста

| Статус       | Значение                                             |
|--------------|------------------------------------------------------|
| `queued`     | запланирован, ждёт публикации                        |
| `publishing` | (зарезервировано) взят в работу — защита от дублей   |
| `published`  | успешно опубликован                                  |
| `error`      | публикация упала после исчерпания попыток            |

## Retry и логирование

- При ошибке публикации планировщик увеличивает `retry_count` и оставляет пост в `queued`.
- После **3** неудачных попыток статус переводится в `error`, текст ошибки — в `last_error`.
- Ответ платформы (например `message_id`) пишется в `result` для аудита.
- Таблица `post_logs` предусмотрена под детальный по-канальный журнал (опционально).

## Честно про ограничения

- Публикация медиа для Telegram в заготовке упрощена (шлётся текст); для фото/видео
  добавьте отдельную ветку `sendPhoto`/`sendVideo`.
- Нет «взятия в работу» через `publishing` в SQL-транзакции — при нескольких воркерах
  возможны гонки; для продакшена добавьте `UPDATE ... SET status='publishing' ... RETURNING`
  с `FOR UPDATE SKIP LOCKED`.
- VK/OK/Дзен — только каркас HTTP-ноды, без реальной авторизации.
